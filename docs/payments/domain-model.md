# Payments — domain model

The single subdomain of [Payments](README.md). Terms are in the [glossary](glossary.md); sequence diagrams are in [flows.md](flows.md). Each business rule becomes a `Rule:` in a feature next to this file.

## Aggregates

| Aggregate | Root entity | Invariants it protects                                                                                                                                                    | Changed by                       |
| --------- | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| `Payment` | `Payment`   | At most one payment is stored per order, under its order id (2, 7, 13). Its amount is an integer greater than 0 (1, 6). Only a `Captured` payment can be refunded (4, 8). | `ChargePayment`, `RefundPayment` |

## Entities

| Entity    | Identity                 | Attributes                                | Inside aggregate | Lifecycle                                                                                                                                                                                                                                       |
| --------- | ------------------------ | ----------------------------------------- | ---------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Payment` | `OrderId`, one per order | `orderId`, `amount`, `currency`, `status` | `Payment`        | `Pending` → `Captured` or `Failed`; `Captured` → `Refunded`. A `Failed` or `Pending` payment is replaced by the next charge of its order (7, 13). `Pending` is stored before the gateway is called and stays while its outcome is unknown (12). |

## Value objects

| Value object | Attributes                     | Validation                                                         | Used by   |
| ------------ | ------------------------------ | ------------------------------------------------------------------ | --------- |
| `Amount`     | `value` (integer, minor units) | Greater than 0 and an integer, else `INVALID_AMOUNT` (rules 1, 6). | `Payment` |

## Business rules

Numbered; every validation cites one; state precedence when several can hold; `<` vs `<=` spelled. `Source` is `decided[ — <reason>]` or `assumed`, and an `assumed` rule may only back a `@draft` feature. Error codes are CAPS tokens in backticks.

Rules 1 to 5 were approved by the user on 2026-10-08. Rules 6 to 11 fill gaps the approved rules leave open; the simplest reading was taken and the user confirmed them on 2026-10-09. Rules 12 to 14 close the gaps the F2 review found in `ChargePayment` (a double charge and an unknown outcome); the user decided them on 2026-10-09 (F2b).

| #   | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | Source                           |
| --- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| 1   | The amount is greater than 0 (`amount > 0`). Zero and negative amounts are refused with `INVALID_AMOUNT` and nothing is stored.                                                                                                                                                                                                                                                                                                                                                          | decided                          |
| 2   | There is one successful charge per order, with the order id as the idempotency key. Charging an order that already has one returns the existing charge and charges nothing more, whatever amount or token the new request carries.                                                                                                                                                                                                                                                       | decided                          |
| 3   | When the gateway declines the charge, the payment is stored as `Failed` and the charge is refused with `PAYMENT_DECLINED`.                                                                                                                                                                                                                                                                                                                                                               | decided                          |
| 4   | Only a `Captured` payment can be refunded; refunding any other payment is refused with `PAYMENT_NOT_REFUNDABLE`.                                                                                                                                                                                                                                                                                                                                                                         | decided                          |
| 5   | A charge takes an opaque `paymentMethodToken` and never card data. The gateway receives the token; the payment keeps none. The fake gateway declines `tok_decline` and captures any other token.                                                                                                                                                                                                                                                                                         | decided                          |
| 6   | The amount is an integer in minor units; a fractional amount is refused with `INVALID_AMOUNT`.                                                                                                                                                                                                                                                                                                                                                                                           | decided                          |
| 7   | Only a `Captured` or `Refunded` payment counts as the order's successful charge (rule 2). Charging an order whose payment is `Failed` charges again and replaces the failed payment, so the customer can retry.                                                                                                                                                                                                                                                                          | decided                          |
| 8   | Refunding an order that has no payment is refused with `PAYMENT_NOT_REFUNDABLE`, like a payment that is not `Captured` (rule 4).                                                                                                                                                                                                                                                                                                                                                         | decided                          |
| 9   | A refund changes the payment only; the gateway has no refund operation in this slice.                                                                                                                                                                                                                                                                                                                                                                                                    | decided                          |
| 10  | When several refusals hold, `INVALID_AMOUNT` wins: the amount is checked before an existing payment is looked up, so an invalid amount is refused even when the order is already charged.                                                                                                                                                                                                                                                                                                | decided                          |
| 11  | The currency is carried as the caller gives it and not re-checked; ordering guarantees three uppercase letters.                                                                                                                                                                                                                                                                                                                                                                          | decided                          |
| 12  | A charge stores the payment as `Pending` before it calls the gateway, then moves it to `Captured` or `Failed` from the outcome (rule 3). When the gateway gives no answer (it throws, for example on a timeout), the payment stays `Pending` and the error propagates: the outcome is unknown, so nothing is guessed.                                                                                                                                                                    | decided — user, 2026-10-09 (F2b) |
| 13  | A `Pending` payment does not count as the order's successful charge (rule 7). Charging an order whose payment is `Pending` calls the gateway again with the same idempotency key and resolves the payment to `Captured` or `Failed`; the gateway takes the money once (rule 14).                                                                                                                                                                                                         | decided — user, 2026-10-09 (F2b) |
| 14  | The gateway is given the order id as the idempotency key and honours it: a repeated charge with the same key returns the first successful outcome and takes no more money, also when two charges for one order run at the same time. A declined charge is not remembered, so a retry after a decline charges again (rule 7). `Payments.startCharge` checks the order's payment and stores the new `Pending` in one step, so a late concurrent charge never overwrites a charged payment. | decided — user, 2026-10-09 (F2b) |

## Driven ports

`Adapter today` starts with `Memory` or `@<context>` (another context's barrel). `Contract` is the invariant every implementation keeps, in-memory or real.

| Port             | Answers                                                                                       | Adapter today                                                                                                                                 | Contract                                                                                                                                                                                                                                                                         |
| ---------------- | --------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Payments`       | `byOrderId(orderId) → Payment \| null`, `save(payment)`, `startCharge(pending) → Payment`     | Memory: a process-local map, lost on restart.                                                                                                 | `byOrderId` returns what `save` last stored under that order and `null` for an order never saved. `startCharge` returns the order's charged payment if it has one; otherwise it stores the given `Pending` payment and returns it, as one step.                                  |
| `PaymentGateway` | `charge({ amount, currency, paymentMethodToken, idempotencyKey }) → 'Captured' \| 'Declined'` | Memory: a fake gateway that declines `tok_decline` and captures any other token; it translates the gateway's own result at the adapter (ACL). | The answer is one of the two domain outcomes, or the call throws when the gateway gives no answer. A repeated key returns the first `Captured` outcome and takes no more money; a decline is not remembered. A gateway type never crosses the port, and the token is never kept. |

## Driving adapters

`Route` is `METHOD /<resource>[/path]` under the API's global prefix. `Answers` lists the statuses; the first 2xx is the success status. `Caller` is who may call and where the identity comes from; request bodies never carry `userId`, `accountId` or `actorId`.

`ChargePayment` and `RefundPayment` have no route: ordering calls them through this context's barrel.
