# Payments — domain model

The single subdomain of [Payments](README.md). Terms are in the [glossary](glossary.md); sequence diagrams are in [flows.md](flows.md). Each business rule becomes a `Rule:` in a feature next to this file.

## Aggregates

| Aggregate | Root entity | Invariants it protects                                                                                                                                                    | Changed by                       |
| --------- | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------- |
| `Payment` | `Payment`   | At most one payment is stored per order, under its order id (2, 7, 13). Its amount is an integer greater than 0 (1, 6). Only a `Captured` payment can be refunded (4, 8). | `ChargePayment`, `RefundPayment` |

## Entities

| Entity    | Identity                             | Attributes                                                            | Inside aggregate | Lifecycle                                                                                                                                                                                                                                                                                                                         |
| --------- | ------------------------------------ | --------------------------------------------------------------------- | ---------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Payment` | `PaymentId`; one per order at a time | `id`, `orderId`, `amount`, `currency`, `paymentMethodToken`, `status` | `Payment`        | `Pending` → `Captured` or `Failed`; `Captured` → `Refunded`. A `Failed` payment is replaced by a new payment, with a new id, at the next charge of its order (7, 14). A `Pending` payment is kept and resolved by that charge (13). `Pending` is stored before the gateway is called and stays while its outcome is unknown (12). |

## Value objects

| Value object | Attributes                     | Validation                                                         | Used by   |
| ------------ | ------------------------------ | ------------------------------------------------------------------ | --------- |
| `Amount`     | `value` (integer, minor units) | Greater than 0 and an integer, else `INVALID_AMOUNT` (rules 1, 6). | `Payment` |

## Business rules

Numbered; every validation cites one; state precedence when several can hold; `<` vs `<=` spelled. `Source` is `decided[ — <reason>]` or `assumed`, and an `assumed` rule may only back a `@draft` feature. Error codes are CAPS tokens in backticks.

Rules 1 to 5 were approved by the user on 2026-10-08. Rules 6 to 11 fill gaps the approved rules leave open; the simplest reading was taken and the user confirmed them on 2026-10-09. Rules 12 to 15 close the gaps the F2 review found in `ChargePayment` (a double charge and an unknown outcome, and a late save over a new payment); the user decided them on 2026-10-09 (F2b, F2c).

| #   | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | Source                                                                      |
| --- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------- |
| 1   | The amount is greater than 0 (`amount > 0`). Zero and negative amounts are refused with `INVALID_AMOUNT` and nothing is stored.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | decided                                                                     |
| 2   | There is one successful charge per order, looked up by its order id. Charging an order that already has one returns the existing charge and charges nothing more, whatever amount or token the new request carries.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                  | decided; amended 2026-10-09 (F2b, user: the payment id is the key)          |
| 3   | When the gateway declines the charge, the payment is stored as `Failed` and the charge is refused with `PAYMENT_DECLINED`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | decided                                                                     |
| 4   | Only a `Captured` payment can be refunded; refunding any other payment is refused with `PAYMENT_NOT_REFUNDABLE`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | decided                                                                     |
| 5   | A charge takes an opaque `paymentMethodToken` and never card data. The gateway receives the token, and the payment keeps the opaque token of its request so that a `Pending` retry can resolve it (rule 13). The fake gateway declines `tok_decline` and captures any other token.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | decided — user, 2026-10-08; amended 2026-10-09 (F2b)                        |
| 6   | The amount is an integer in minor units; a fractional amount is refused with `INVALID_AMOUNT`.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                       | decided                                                                     |
| 7   | Only a `Captured` or `Refunded` payment counts as the order's successful charge (rule 2). Charging an order whose payment is `Failed` charges again and replaces the failed payment, so the customer can retry.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | decided                                                                     |
| 8   | Refunding an order that has no payment is refused with `PAYMENT_NOT_REFUNDABLE`, like a payment that is not `Captured` (rule 4).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | decided                                                                     |
| 9   | A refund changes the payment only; the gateway has no refund operation in this slice.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                | decided                                                                     |
| 10  | When several refusals hold, `INVALID_AMOUNT` wins: the amount is checked before an existing payment is looked up, so an invalid amount is refused even when the order is already charged.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | decided                                                                     |
| 11  | The currency is carried as the caller gives it and not re-checked; ordering guarantees three uppercase letters.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | decided                                                                     |
| 12  | A charge creates the payment as `Pending`, with an id of its own, and stores it before it calls the gateway, then moves it to `Captured` or `Failed` from the outcome (rule 3). When the gateway gives no answer (it throws, for example on a timeout) the payment stays `Pending` and the error propagates: the outcome is unknown, so nothing is guessed.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | decided — user, 2026-10-09 (F2b); amended 2026-10-09 (F2b follow-ups, user) |
| 13  | A `Pending` payment does not count as the order's successful charge (rule 7). Charging an order whose payment is `Pending` resolves that same payment with its stored request (amount, currency and token), under its own idempotency key; the retry's own amount and token are not used. If the first request reached the gateway, it replays its outcome and the money is taken once (rule 14). The payment becomes `Captured` or `Failed`; a `Failed` payment is replaced by the next charge (rule 7).                                                                                                                                                                                                                                                                                                                                                                                                                            | decided — user, 2026-10-09 (F2b); amended 2026-10-09 (F2b follow-ups, user) |
| 14  | The idempotency key of a charge is the id of its payment, not the order id. The gateway saves the outcome of the first request made with a key, `Captured` or `Declined`, and replays it for every later request with that key; it refuses a request whose parameters differ from the first, which only guards against a programming error because a retry always resends the stored request; and it saves nothing when it gives no answer, so that request can be retried. A `Failed` payment is replaced by a new payment with a new id, so the retry in rule 7 is a new request that charges again. Two charges for one order that run at the same time share the `Pending` payment and its key, so the money is taken once. `Payments.startCharge` answers the order's payment unless it is absent or `Failed`, and otherwise stores the new `Pending` one, as one step, so a late concurrent charge never overwrites a payment. | decided — user, 2026-10-09 (F2b); amended 2026-10-09 (F2b follow-ups, user) |
| 15  | A payment is saved only over the payment it came from: `Payments.save` stores it unless the order holds a payment with another id, in which case it changes nothing, so the late save of a payment that a new one replaced (rule 14) never overwrites the new one.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | decided — user, 2026-10-09 (F2c)                                            |

## Driven ports

`Adapter today` starts with `Memory` or `@<context>` (another context's barrel). `Contract` is the invariant every implementation keeps, in-memory or real.

| Port             | Answers                                                                                                           | Adapter today                                                                                                                                                                                                                                                                                                                                                                                                                                                                                     | Contract                                                                                                                                                                                                                                                                                                                                                                                                                        |
| ---------------- | ----------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Payments`       | `byOrderId(orderId) → Payment \| null`, `save(payment)` (only over the same id), `startCharge(pending) → Payment` | Memory: a process-local map, lost on restart.                                                                                                                                                                                                                                                                                                                                                                                                                                                     | `byOrderId` returns what `save` last stored under that order and `null` for an order never saved. `save` leaves the stored payment alone when it has another id, the check and the store being one atomic step: a compare-by-id check keeps the port to the one method. `startCharge` returns the order's payment unless it has none or it is `Failed`; then it stores the given `Pending` payment and returns it, as one step. |
| `PaymentGateway` | `charge({ amount, currency, paymentMethodToken, idempotencyKey }) → 'Captured' \| 'Declined'`                     | Memory: a fake gateway that declines `tok_decline` and captures any other token, remembers the outcome per idempotency key and refuses a key reused with other parameters with a `GatewayError`; it translates the gateway's own result at the adapter (ACL). The semantics copy [Stripe's idempotent requests](https://docs.stripe.com/api/idempotent_requests): the outcome of the first request for a key is saved, a failure included, and a later request with other parameters is an error. | The answer is one of the two domain outcomes, or the call throws when the gateway gives no answer. A repeated key replays the first outcome, `Captured` or `Declined`, and takes no more money; the same key with other parameters is refused; a call that gives no answer is not remembered. A gateway type never crosses the port, and the token is never kept.                                                               |
